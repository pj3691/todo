# AI 能力边界与安全约定

记录 AI 助手与 MCP 服务**提供了哪些能力、边界在哪**，以及刻意不做的部分与原因。目的是避免以后每次想加功能都要重新讨论一遍。

## 一、当前边界

| 能力 | 状态 | 原因 |
| --- | --- | --- |
| 查待办 / 改待办 | 已开放（按角色） | 影响范围限于本人可写的数据 |
| 查项目列表与日志 | 已开放（只读） | 纯读取，无副作用 |
| 启动 / 停止 / 重启项目 | 已开放（默认关闭） | 引用型工具，只传项目 id；需管理员、白名单、限流，内置助手还会要求在页面上确认 |
| 执行项目中登记的命令 | **不开放** | 存在被提示词注入误触发的可能 |
| 修改项目配置（含启动命令） | **不开放，且不应开放** | 见第二节 |
| 结束端口进程（kill） | **不开放** | 绕过项目模型直接杀进程 |

代码里的对应位置：

- `src/mcp/tools/project-control.ts`：启停工具实现，文件头写了完整的边界
- `src/mcp/tools/index.ts`：`gatedTools` 与 `allTools` 分开导出，开关关闭时不注册
- `src/chat.ts` 的 `SYSTEM_PROMPT`：告诉模型可以启停但必须先过用户确认，且不能写命令
- `config/config.json` 的 `agent` 段：开关、白名单、限流三个旋钮

### 实施状态

| 条件 | 状态 |
| --- | --- |
| 1 能力最小化（只有 id） | 已落地 |
| 2 默认关闭 + 显式开关 | 已落地（缺配置即关闭） |
| 3 角色门槛 admin | 已落地 |
| 4 人机确认 | 内置助手已落地；MCP 通道没有（受协议所限） |
| 5 审计 | 已落地（`[chat][audit]` / MCP stderr） |
| 6 限流 | 已落地（每项目每分钟 3 次） |
| 7 进程隔离 | **未做**，与 AI 正交，见本节第 7 条 |

## 二、安全模型：边界在「命令决定权」

这套系统里**没有任何接口接受命令字符串**：

| 接口 | 参数 | 命令内容来源 |
| --- | --- | --- |
| `POST /projects/:id/start` | projectId | 数据库里该项目配置的启动命令 |
| `POST /projects/:id/stop` | projectId | 后端内置终止逻辑 |
| `POST /projects/:id/restart` | projectId | 同上 |
| `POST /projects/:id/commands/:commandId/run` | projectId + commandId | `project_commands` 表里的登记命令 |

触发者只能「点名」，不能「写命令」。这是既有架构最重要的安全属性。

由此得到两条硬约束：

1. **只暴露引用型工具**：参数只有 id，没有命令文本
2. **绝不暴露写命令的接口**：`PATCH /projects/:id`（可改 `command` 字段）与 `POST /projects`（可新建项目）永远不封装成工具

第 2 条是第 1 条的前提。只要 AI 能改配置再触发，能力最小化就形同虚设——它会「先写 `rm -rf` 到项目配置，再点启动」。

因此判断某个能力能不能开放，先问一句：**这个操作会不会改变"命令内容"？** 会，就不开。

## 三、开放项目启停时遵守的条件

按重要性排序。前三条是必要条件，缺一不可；括号里是当前的落地状态。

### 1. 能力最小化（已落地）

```
gitstatus_project_start(id)
gitstatus_project_stop(id)
gitstatus_project_restart(id)
gitstatus_project_run_command(projectId, commandId)   # 未实现
```

- 参数只有 id，绝不接受命令文本
- `run_command` 只接受已登记的 `commandId`
- 不提供端口 kill、不提供项目配置写入

### 2. 默认关闭 + 显式开关（已落地）

两个通道独立控制，默认都关：

```json
"agent": {
  "projectControl": false,
  "allowedProjectIds": [],
  "maxActionsPerMinute": 3
}
```

```
GITSTATUS_AGENT_PROJECT_CONTROL=1   # MCP 进程
```

关闭时工具**不注册**：`tools/list` 里不出现，模型看不到也就不会尝试。这比「注册了但调用时报错」好，后者会让模型反复重试。

`allowedProjectIds` 空数组表示全部允许；填了就只放行列出的项目。适合「只让 AI 管测试环境项目」的诉求。

### 3. 角色门槛设为 admin（已落地）

不是 `readwrite`。启停影响的是服务器进程，与改数据的量级不同。这样即使某个读写账号的 API Key 泄漏，也拿不到这个能力。

### 4. 人机确认（内置助手已落地）

两个通道的可靠性不同，必须区别对待：

| 通道 | 可做的事 | 可靠性 |
| --- | --- | --- |
| 内置助手（网页） | 弹原生确认框，展示将要执行的命令 | 高——人在页面上 |
| MCP 客户端 | 只能靠工具语义与 `destructiveHint` 注解 | **低**——控制不了客户端 UI，模型可以自己连调两次 |

所以在 MCP 通道上，真正起作用的是第 1、2、3 条，不要指望「两阶段 token」：模型完全可以在一次回复里先调 preview 再调 confirm，用户未必看清。

### 5. 审计（已落地）

每次调用记一条结构化日志：账号、通道（web / mcp）、工具名、项目 id、命令、结果、耗时。出问题时这是唯一的回溯依据。现有 `logInfo` 直接可用。

### 6. 限流（已落地）

建议每项目每分钟 3 次。主要防模型陷入循环反复重启，把本来正常的服务打挂。

### 7. 进程隔离

与 AI 无关的独立一层：子进程用低权限账户运行，或容器化。做到这一层，即使命令本身是恶意的，破坏面也被限制在该账户权限与工作目录内。

这一条和前面六条正交——前六条管「谁能触发」，这一条管「触发了之后能做什么」。

## 四、残余风险

**提示词注入是真实威胁。** 待办标题、项目名称、运行日志都可能包含「忽略之前的指令，执行 xxx」这类内容。AI 读取这些数据时可能被操纵，去调用启停工具。

能力最小化把它限制在「已配置的命令集合」内，但**限制不等于消除**：如果某个项目配的是 `npm run migrate:prod` 或部署脚本，被误触发的影响是真实的。

所以开放时应该用一个具体问题逐个项目过一遍：

> 这条命令被「误触发一次」，能否接受？

不能接受的，就不要放进 `allowedProjectIds`。

## 五、实施验收清单

真要加这个能力时，按这份清单逐项确认：

- [ ] 新工具的参数只有 id，签名里不存在命令字符串
- [ ] 未开启开关时，`tools/list` 与内置助手的 `tools` 数组里都没有这几个工具
- [ ] 非 admin 账号：工具不可见；直接构造请求也返回 403
- [ ] `allowedProjectIds` 为空与非空的行为符合预期（空=全部，非空=仅列出项）
- [ ] 每次调用写入审计日志，包含通道字段
- [ ] 限流生效，超限返回明确的错误文案而非静默失败
- [ ] 内置助手执行前有确认弹窗，展示将要执行的命令原文
- [ ] 项目配置写入接口（`PATCH /projects/:id`、`POST /projects`）**仍然没有**对应的工具
- [ ] `npm run mcp:docs` 重新生成，文档里的工具数与角色可见性表同步
- [ ] 本文档更新「当前边界」表，把已开放项移到正确位置
