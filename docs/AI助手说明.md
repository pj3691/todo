# AI 助手说明

工作区内置的对话页（`/pages/chat.html`）：用自然语言读写待办、查项目状态、启停项目。它和 MCP 服务共用同一份工具定义，区别只在于谁来调模型。

## 一、两种用法怎么选

| | 内置助手（本页） | MCP 客户端（Qoder / Claude Desktop） |
| --- | --- | --- |
| 模型由谁提供 | GitStatus 后端，需自己配 key | 客户端已配好的模型，**不用另买** |
| 界面在哪 | 本仓库的对话页 | 客户端自己的对话框 |
| 需要什么凭据 | 登录态即可 | 账号页创建的 `gsk_` API 密钥 |
| 适合场景 | 不想开 IDE、只想快速问两句 | 已经在写代码，顺手让模型查数据 |

两者可以同时用，工具定义只有一份（[src/mcp/tools](../src/mcp/tools)），不会出现「MCP 能查、助手不能查」的偏差。MCP 侧细节见 [MCP工具说明.md](./MCP工具说明.md)。

## 二、配置模型

### 推荐：页面里填

用管理员账号进入「AI 助手」，点右上角齿轮：

| 字段 | 说明 |
| --- | --- |
| 接口地址 `baseUrl` | OpenAI 兼容地址，**要带 `/v1`**。DeepSeek、智谱、通义、Kimi、Ollama 都可 |
| 模型 `model` | 需要支持 function calling |
| API Key | 保存后不再回传前端；留空表示沿用已保存的值 |
| 温度 `temperature` | 默认 0.3，工具调用场景不建议调高 |
| 最大工具轮数 | 一次提问最多跑几轮工具调用，默认 6，上限 20 |

面板底部三个按钮：

- **测试连接**：用当前表单值发一次 `max_tokens: 1` 的最小请求，可以先测再存
- **保存**：写入后立即生效，不需要重启
- **清除保存的配置**：删掉页面保存的值，回退到下层来源

没配置时页面顶部会给出提示并禁用输入框，不会静默失败。

### 三种来源与优先级

```
页面保存  >  环境变量  >  config/config.json
```

顺序和 DSH 的凭据层一致：用户在界面上明确保存过的值必须一致生效，环境变量只在没有保存值时兜底。设置面板顶部会显示**当前来源**，所以「改了环境变量却不生效」时能一眼看出原因——点「清除保存的配置」即可回退。

| 来源 | 存放位置 | 适合 |
| --- | --- | --- |
| 页面保存 | `src/output/llm-credentials.json` | 日常使用；该目录已被 `.gitignore` 忽略 |
| 环境变量 | `GITSTATUS_LLM_BASE_URL` / `GITSTATUS_LLM_API_KEY` / `GITSTATUS_LLM_MODEL` | 容器、CI、不想落盘的场景 |
| 配置文件 | `config/config.json` 的 `llm` 段 | 部署默认值，仓库里带一份空 key 的模板 |

环境变量需要重启后台；另外两种改完即时生效。

### 密钥怎么存

- 接口只返回掩码（`sk-••••cdef`）与来源，**明文不出后端**；读接口的返回类型里没有能放明文的字段
- 存储文件放在 `src/output/` 而不是 `config/`，因为 `config/config.json` 被 git 跟踪，密钥写进去迟早进仓库
- 写入用原子替换（先写临时文件再改名），避免半截文件
- POSIX 下文件按 `0600` 写入并在读取时校验；Windows 没有对应语义，不做假检查
- 只有管理员能改：`PUT` / `DELETE /chat/llm` 对 `readonly`、`readwrite` 返回 403；读取对所有登录用户开放

### 配置文件长什么样

如果选择用 `config/config.json` 作为部署默认值：

```json
{
  "llm": {
    "baseUrl": "https://api.deepseek.com",
    "apiKey": "sk-你的密钥",
    "model": "deepseek-flash",
    "temperature": 0.3,
    "maxToolRounds": 6,
    "timeoutMs": 60000
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `baseUrl` | OpenAI 兼容地址，要带 `/v1` |
| `apiKey` | 留空则视为未配置 |
| `model` | 需要支持 function calling |
| `temperature` | 默认 0.3 |
| `maxToolRounds` | 默认 6，上限 20 |
| `timeoutMs` | 单轮 LLM 请求超时，默认 60 秒 |

### 常见服务商

| 服务商 | baseUrl | 模型示例 |
| --- | --- | --- |
| DeepSeek | `https://api.deepseek.com` | `deepseek-flash`（V4.1-Flash）/ `deepseek-v4-pro` |
| 智谱 | `https://open.bigmodel.cn/api/paas/v4` | `glm-4.6` |
| 通义 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 本地 Ollama | `http://127.0.0.1:11434/v1` | `qwen2.5:14b` |

> DeepSeek 的旧模型名 `deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 停用，`deepseek-v4-flash` 也已下线（仍可调用但会被路由到 V4.1-Flash）。当前请用 `deepseek-flash` 或 `deepseek-v4-pro`，两者都支持工具调用。

## 三、界面

进入导航栏「AI 助手」即用，需要先登录。

- **左侧**：历史会话列表，点「+ 新对话」开新会话，悬停出现删除按钮；底部两行分别是「模型 + 可用工具数」与本会话用量（`↑上下文 ↓输出 · 命中 x% · N 次请求`），点用量那行打开明细
- **中间**：消息流。助手的回复按 Markdown 渲染（标题、列表、表格、代码块、链接），原始 HTML 先经 DOMPurify 消毒再插入页面；每次工具调用都渲染成一张可折叠卡片，展开能看到调用参数与完整结果，失败的卡片自动展开；每条助手消息下方显示本轮 token 用量与命中率
- **右上角**：柱状图按钮打开「会话用量」弹窗（登录即可见）；齿轮是管理员专属的模型设置
- **底部**：输入框。`Enter` 发送、`Shift + Enter` 换行；生成过程中「发送」变成「停止」
- 首条消息自动截取前 24 字作为会话标题

### 附件

输入框左侧的回形针、直接拖文件进对话区、粘贴剪贴板图片，三条路都能加附件，一次最多 5 个：

| 限制 | 值 |
| --- | --- |
| 单个文件 | 32 MB（图片 8 MB） |
| 后缀 | 与待办附件一致，拦截 `.exe` / `.bat` / `.ps1` / `.sh` / `.jar` 等 |
| 可执行文件 | 拒绝，提示具体文件名 |

选中即上传，附件 chip 上会显示「上传中…」直到拿到编号；上传未完成时发送按钮禁用。发送后 chip 移到用户消息下方，模型收到的上下文里会多出一段编号清单：

```
[本条消息附带的文件。需要随待办一起保存时，把编号填进 attachmentIds]
- #12 报价单.xlsx（1.2 MB）
```

**模型不读文件内容**，它只能看到文件名与编号。需要文件跟着待办走时，工具调用会带上 `attachmentIds`，后端把暂存文件转投到待办附件目录；绑定成功的 chip 显示「已加入 #337」。

- 新建和修改待办都支持附件；修改是追加，不会覆盖原有附件
- 附件编号只能引用本会话里列出的那些，编造编号或抄别的会话会被工具直接拒绝
- 已经绑定过的附件不能重复使用；未发送就移除的附件会从暂存区删除
- MCP 客户端没有对话上下文，传 `attachmentIds` 会报错——那里只能建纯文字待办

点「停止」会立即中断：**已经生成的内容会保留并落库**，消息下方标注「该回复被中断」，不会整段丢失。

### 用量与缓存命中

provider 返回的 usage 会落进 `payload.usage`，按四个不重叠的桶存：

| 桶 | 含义 |
| --- | --- |
| `inputTokens` | 未命中缓存的 prompt |
| `cacheReadTokens` | 命中前缀缓存的 prompt |
| `cacheWriteTokens` | 写入缓存的 prompt |
| `outputTokens` | 输出 |

命中率 = `cacheRead / (input + cacheRead + cacheWrite)`，分母不含输出。provider 没报缓存字段时显示「—」，不当作 0，避免把「不支持缓存」误读成「每次都 miss」。

一次工具循环会对同一个问题多次请求模型，这些用量会**累加**到同一条助手消息上并记 `requests` 次数；逐轮明细因此按消息归并，而不是按 HTTP 请求。每条助手消息另外在 `payload.requests` 里保留**逐次**用量（含 `round` 与 `contextTokens`），排查「哪一次开始不命中」时看这个字段。

> system prompt 里只放**日期**（每天变一次），精确时刻靠 `gitstatus_now` 工具。原因：前缀缓存是按字节比对开头的，之前把精确到秒的时间拼进 system，导致每轮请求的缓存从第一个字就失效，命中率恒为 0。

#### 命中率为什么偏低，以及做了什么

前缀缓存是**异步写入**的。实测同一 7.5k token 前缀连续请求：

| 重发间隔 | 命中 |
| --- | --- |
| 立即（<1s） | **0%** |
| 等待 2s | 98% |
| 等待 5s | 98% |
| 追加一轮对话后（已等待） | 97.9% |

工具执行往往只要几十毫秒，紧接着发下一次请求，上一轮刚写好的缓存还没落盘，那一段就白存了。这是之前长会话命中率只有 50% 左右的主因，不是消息结构问题。

对应的四处处理：

1. **工具轮次之间等一个缓存窗口**。上下文超过 8k tokens 时，两次请求至少隔 2 秒；工具本身已经跑够时间的就不再等。阈值与窗口是常量加配置：

   ```json
   "llm": { "cacheGapMs": 2000 }
   ```

   也可用环境变量 `GITSTATUS_LLM_CACHE_GAP_MS` 覆盖，设为 `0` 关闭等待。实测把工具轮次第二次请求从「几乎全 miss」拉到 99.3% 命中，代价是单轮多约 2 秒。

2. **身份写进 system**。账号与角色直接给出，模型不必为确认权限多调一次 `gitstatus_whoami`——少一次请求就少一次缓存断裂。副作用是角色变更会让当前会话失效一次。

3. **逐次用量落库**。合并后的 `usage` 看不出单次命中，`payload.requests` 保留每次请求的桶值与上下文规模。

4. **压缩工具输出**。工具结果是每轮新增内容里最大的一块，而新增内容必然 miss。`gitstatus_project_list` 默认只回 id、名称、状态与 pid（17 个项目从约 2.7k 字符降到 0.8k），启动命令、路径、自定义命令需要 `verbose=true`；两个日志工具的默认条数从 100 降到 40。确认启动时仍会看到命令原文——那是页面上的确认卡片，不占模型上下文。

命中率的上限就摆在那里：每次请求的「工具调用声明 + 工具结果 + 本轮新回答」都是新增 token，必然计为 miss。长会话几个工具轮次跑下来，**94% 左右就是上限**；看到 89% 时应该先看逐次明细，如果除了一两次「工具结果」轮之外都在 96% 以上，就说明结构没问题了。

仍会有天然 miss：跨天继续同一会话（日期行变了）、缓存过期后的第一轮、末尾不足一个缓存块的部分。

#### 面板上的数字看哪个

| 位置 | 口径 | 用途 |
| --- | --- | --- |
| 底部用量行 | **最近一轮**命中率 | 看缓存现在工作得好不好 |
| 弹窗「命中（最近一轮）」 | 同上 | 与底部一致 |
| 弹窗「命中（累计）」 | 会话全部请求 | 算钱、回看历史成本 |
| 弹窗逐轮表 | 每条助手消息的合并值 | 定位具体哪一轮异常 |

新会话第一次请求要把 system 与工具定义写进缓存，这一笔必然全 miss（实测约 4.5k tokens）。如果只改了一行代码，它会直接体现在累计命中率上；但在它之后新建的任何会话，首轮可以命中同一段前缀（实测 97%）。所以看到「累计 74% 但最近一轮 96%」是正常的：前者是历史，后者是现状。


## 四、工具与权限

助手能用的工具就是当前账号角色可见的那部分：

| 角色 | 可见工具（开关关） | 可写工具 | 开关开启后 |
| --- | --- | --- | --- |
| 只读 | 14 | 0 | 14 |
| 读写 | 27 | 13 | 27 |
| 管理员 | 27 | 13 | 30（多 3 个启停） |

具体清单见 [MCP工具说明.md](./MCP工具说明.md#五工具清单自动生成)。

两个要点：

1. **执行身份是发起对话的人**。工具调用会带上当前登录用户的 token 去请求本机接口，所以归属校验、共享权限、只读拦截和后端完全一致，不存在「助手绕过权限」的路径。
2. **项目启停是开关能力**。需要 `config/config.json` 的 `agent.projectControl` 为 `true`，且账号是管理员；关闭时这三个工具在模型上下文里根本不存在。命令执行、端口结束、项目配置写入永远不封装。

> 为什么这样分层、还留有哪些残余风险，见 [AI能力边界与安全约定.md](./AI能力边界与安全约定.md)。

### 项目启停

开启后管理员可以用自然语言让助手启动/停止/重启项目，但每一道门槛都是硬约束：

| 层 | 行为 |
| --- | --- |
| 开关 | `agent.projectControl`，缺省关闭；关闭时不注册工具 |
| 角色 | 最低 `admin`，读写账号看不到 |
| 白名单 | `agent.allowedProjectIds`，空表示全部 |
| 限流 | 每项目每分钟 3 次（`maxActionsPerMinute`），防模型循环重启 |
| 人工确认 | 内置助手会推一张确认卡片，展示项目名、当前状态与启动命令原文，60 秒未响应视为拒绝 |
| 参数 | 只有项目 id，没有命令文本；命令永远来自项目配置 |
| 审计 | 每次调用写一条 `[chat][audit]` 日志，含通道、项目、结果、耗时 |

确认卡片的按钮是「拒绝」与「允许执行」；流中断或超时后卡片会变成「已失效」，避免留下能点但服务端已不等了的按钮。MCP 通道没有确认能力，靠上面的开关与角色兜底。

## 五、数据存储

三张表，都在 `src/output/gitstatus.db`：

```
chat_sessions    id(TEXT, UUID) / user_id / title / model / created_at / updated_at
chat_messages    id / session_id / role(user|assistant) / content / payload(JSON) / created_at
chat_attachments id / user_id / session_id / kind / original_name / stored_name
                 / mime_type / size / bound_todo_id / bound_attachment_id / created_at
```

- 会话按 `user_id` 隔离，接口层每次都校验归属，看不到别人的会话
- 工具调用结果存在 `payload.toolCalls` 里，包含参数、结果、是否失败，供前端展开
- token 用量存在 `payload.usage` 里（四桶 + `requests`），历史数据只有 `{prompt, completion}` 两桶时按「全部未命中」兼容读取
- 用户消息的附件快照存在 `payload.attachments`，存文件名、大小与编号，不存二进制
- 删除会话会连带删除消息（外键级联）；同时清掉该会话未绑定的暂存附件
- 删除用户时其会话一并清理

附件文件分两处：

| 目录 | 内容 | 清理时机 |
| --- | --- | --- |
| `src/output/chat-uploads/<user_id>/` | 尚未绑定到待办的暂存文件 | 绑定成功后删副本；超过 7 天未绑定在启动时清理 |
| `src/output/todo-images/<user_id>/` | 待办的真实附件 | 由待办页删除附件时清理 |

## 六、已知限制

- **上下文会一直变长**。目前不做裁剪，长对话会持续消耗 token；单次工具结果做了 8000 字截断，但历史消息不截断。对话变慢或变贵时，开新会话最快。
- **没有重试与降级**。LLM 报错就把错误原文显示出来，不自动重试。
- **工具调用是串行的**。一次响应里模型要求调用多个工具时按顺序执行，不并行（避免本机接口压力，也让卡片顺序稳定）。
- **不做流式工具进度**。工具执行期间只显示「执行中…」，中间过程不推送。
- **统计只有 token，没有金额**。命中率与用量来自 provider 的 usage；不同服务商价格不同且会调整，不内置价目表，需要算钱请按官网单价乘 token 数。
- **统计口径依赖 provider**。部分服务商不返回缓存字段，界面上会显示「—」；这种情况下命中率无法优化或验证。
- **没有跨会话汇总**。统计按会话隔离，没有「全部会话总花费」页面。
- **附件不参与推理**。模型只能看到文件名、大小与编号，读不到内容；想让它分析文件内容，目前需要自己把要点贴进对话。
- **Windows 上靠不住文件权限**。`0600` 只对 POSIX 生效，Windows 的保护依赖用户目录本身的 ACL；密钥文件的隔离性不如 Linux/macOS。
